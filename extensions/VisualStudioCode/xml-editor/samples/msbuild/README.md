# MSBuild sample

A workspace for trying the XML editor on MSBuild files. It is not shipped in the extension.

## Try it

1. Open the `xml-editor` folder in VS Code, run `npm ci`, and launch
   **Run XML Editor Extension (MSBuild sample)** (F5). A second VS Code window opens this folder with
   the extension loaded. To try an installed build instead, install the VSIX from the workflow
   artifact and open this folder.
2. Things to try:
   - In `Sample.csproj`, type `<` inside a `PropertyGroup`. Every known property is offered, with
     its documentation. Inside an `ItemGroup` you get items, and inside a `Target` you get tasks.
   - Put the cursor inside `<Nullable></Nullable>` or `<Optimize></Optimize>` and trigger
     completion (Ctrl+Space) to see the suggested values.
   - Type a space after `<PackageReference ` to see its attributes, or after `<Message ` to see
     the task's parameters.
   - Hover over `TargetFramework`, `OutputType`, or `Copy` to read their documentation.
   - Open `Mistakes.csproj` to see five reported errors. Custom properties, items, metadata, and
     tasks are not errors, because MSBuild accepts any name.
   - Run **Format Document** on any file.

`.vscode/settings.json` adds the MSBuild extensions to `xmlEditor.fileExtensions` and registers
the schema twice:
- by file pattern, for SDK-style projects (no namespace);
- by namespace, for legacy projects that declare `xmlns="http://schemas.microsoft.com/developer/msbuild/2003"`.

Copy those two settings into your own workspace or user settings to use the schema elsewhere,
pointing `url` at this folder's `schemas/`.

## The schema

`schemas/` is generated by `Update-MSBuildSchema.ps1` from Microsoft's MSBuild schema in
[dotnet/msbuild](https://github.com/dotnet/msbuild) (MIT; see `schemas/LICENSE.txt`). The release
tag is pinned in the script. The upstream schema lists about 500 properties, 75 items, and 120 tasks,
but using it unmodified causes false errors. The script makes these changes:

| Upstream | Generated |
| --- | --- |
| Targets the `msbuild/2003` namespace, which SDK-style projects do not declare | No namespace. `Microsoft.Build.Namespaced.xsd` uses a chameleon include to put the same components in the 2003 namespace for legacy projects. |
| Only listed property, item, and task names are allowed | Skip wildcards admit any name, as MSBuild does. Listed names still drive completion and hover. |
| Item metadata written as attributes (`<Compile Link="..."/>`) is not allowed | Item types accept any attribute. |
| Boolean and enumerated properties allow no `Condition` and only the literal values listed | Every property accepts `Condition` and `Label`. Values are suggested but not enforced, so `$(Expressions)` are valid. |
| The `MSBuild` task's `RemoveProperties` parameter is missing | Declared. |

Before these changes, the upstream schema produced 185 false errors across 163 real MSBuild files
from the `viu` and `tooling` repositories. The generated schema produces none.

An element next to an overlapping wildcard is valid XSD 1.1, not 1.0, so a strict XSD 1.0 processor
such as `System.Xml.Schema` rejects the generated files. They are meant for editors.

To regenerate, for example after changing the tag:

```powershell
./Update-MSBuildSchema.ps1 -Tag v18.11.0
```

Each change is an exact-match edit with an expected number of matches. If upstream changes
shape, the script fails instead of silently producing a different schema.
